# C15 — Pack Modules

English UI configuration: `shared/products/c15.json`. Domain: `backend/app/products/c15.py`.

A private record is a **packing workspace** containing reusable modules, one current trip, the current checklist at top-level `items`, and archived trip snapshots in `history`. This lets modules be reused between trips while maintaining the shared offline checklist contract. Module changes never modify existing trips.

## Workflow and quantity rules

1. Create a workspace and modules, such as Toiletries, Work or Hiking.
2. Add named items with a positive whole base quantity and a rule: once per trip (`fixed`), per person (`person`), per day (`day`) or per person per day (`person-day`).
3. Include/exclude modules for the next trip. New modules are selected by default.
4. Create a named trip with 1–100 people and 1–365 days. The selected modules are copied into a frozen snapshot. If a current trip exists, its full snapshot and checkmarks are archived first.
5. Review the resulting quantities, then check items as packed. All checked means the trip status is `packed`; unchecking one returns it to `packing`. Clear current checkmarks leaves archived trips intact.

Item labels are compared using Unicode normalization, case folding and collapsed whitespace. Identical labels merge into one checklist row. Within the same quantity rule, the largest base quantity wins across selected modules, preventing accidental doubling when modules overlap. Distinct rules are calculated independently and their totals added. Example: 2 socks/person in Basics and 3 socks/person plus 1 sock/day in Hiking become `max(2,3) × people + 1 × days`. Each resulting row retains the rule calculations and source-module names for review. Within a module, the same canonical label and rule cannot be added twice; remove it before replacing it.

Limits: 50 modules per workspace, 200 items per module, base quantity 1–1000, and 100 archived trips. New workspaces can be used beyond those limits.

## API and offline contract

- `add-module {title}`; `add-module-item {moduleId,label,quantity,rule}`.
- `set-module-selection {moduleId,selected}`.
- `remove-module-item {moduleId,label,rule}` and `remove-module {moduleId}` affect only reusable templates.
- `new-trip {title,people,days}` creates top-level `items` with `{id,label,quantity,checked,rules}` and `currentTrip` with frozen `modules`.
- `toggle-item {itemId,checked}` uses a strict Boolean. The shared application queues this action offline with the original server revision; a revision conflict must be resolved by the user instead of overwriting cloud changes.
- `reset-checks {}` clears only the current checklist.
- `restore-backup {content}` restores a C15 JSON backup into the current record. It validates modules, snapshots, checkmarks and calculated quantities, regenerates domain IDs, and retains server metadata. Invalid backups are rejected atomically. Restore accepts up to 16 MiB of JSON characters so valid larger workspace exports can be read; the shared API still enforces its 12 MiB stored-record limit.

Export TXT for printing or CSV for the current checklist. Common JSON export is the full backup format, including modules and archived trips. CSV is intentionally a checklist export, not a full workspace backup. The domain copies the record before mutation.
