# 标准产品验证计划

更新：2026-09-19｜状态：建议，未执行。适用对象为新增Reddit方向中选定的一项，不同时开发20项。

## 需要分开回答的三个问题

- 任务是否真实存在？Reddit提供线索，仍需要目标用户复述最近一次实际经历。
- 标准产品能否被独立使用并收费？创始人帮用户做完任务不能替代产品可用性。
- AI辅助研发是否划算？必须把人工校核、调试和后续修改一并计入。

## 第一步：拿到任务与替代基线

选择一个具体客户群、一个主要设备或平台、一个高频或高损失任务。由同一批目标用户展示当前做法：表格、纸笔、免费软件、聊天工具或已经付费的系统。

记录任务完成时间、常见错误、使用频次、已有开支，以及他们不换工具的理由。旧帖作者不自动成为可联系的线索；本研究没有发送私信或发帖招募。

## 第二步：用最小完整流程验证

先用界面样例、手工配置或简单可操作原型验证输入、操作和输出。原型是否值得实现，应以明确任务和接触到的用户为前提；不先做账户体系、所有平台版本或大范围集成。

未来进入开发时，以AI辅助实现一个完整任务，记录：

| 记录 | 目的 |
| --- | --- |
| 需求、样例输入与验收结果 | 防止把演示成功当作任务完成 |
| AI工具费用与实际使用时段 | 把开发工具成本单列 |
| 人工设计、审核、修复及发布工时 | 不隐藏AI产出之后的工作 |
| 现成软件或人工流程结果 | 判断是否真有可销售差异 |
| 错误输入、重复操作、导出恢复结果 | 验证确定性工具的可靠性 |
| 关闭模型连接后的功能结果 | 验证“核心无须AI”而非只隐藏AI按钮 |

没有传统研发对照时，只报告这次实际成本，不计算虚构的效率提升倍数。可维护性至少通过一次用户提出的新要求验证，而不是只看初版生成速度。

## 第三步：清楚报价并观察独立使用

按单项档案拟定的价格和范围进行未来试售。展示实际可用的功能、支持周期、数据导出与限制。记录原价、折扣、免费使用分别有多少人；只有真实到账才计付费。

观察用户在没有创始人代操作时能否完成任务，尤其是首次录入、现有数据导入及之后的更新。记录客服次数和总分钟数。对数据清理类产品，先采用只读扫描、预览和用户确认，不以不可逆删除作为试用捷径。

两周内可验证初次采用和一部分重复任务；订阅续费、季节性和长期兼容维护仍须延长观察。低频旅行/收藏工具不能机械套用每日活跃目标，应观察真实任务发生时是否再次使用。

## 第四步：再算投入是否值得

买断情境：

`回收前期投入的销量 = 向上取整(明确列出的固定投入 ÷ 每单扣获客后贡献)`

分母非正时，不存在这个模型下的回本销量。固定投入还应单列持续年度维护；一次买断的研发回本不代表长期现金流成立。

订阅情境：

`某期经营贡献 = 活跃付费客户当期交付贡献合计 − 本期获客支出 − 本期固定维护`

首次配置收费另记。把研发投入除以月度经营贡献，只能得到假设客户数量保持时的回收情境，不能称回收预测；未发生的续费不计入已得收益。

## 继续或暂停

继续标准由具体档案预先定义，并同时检查付款、使用、成本与质量。尤其关注：

- 付费只是支持创始人，还是产品真的替代了原流程？
- 需要手把手服务才能使用，是否已偏离标准产品？
- 免费替代已经满足任务，新产品只减少一两个点击，是否足以覆盖迁移成本？
- 初始数据输入过重，用户是否根本不会维护？
- AI生成的实现需要过多人工修复，是否应该缩小平台、格式和功能范围？

遇到这些情况应修改假设或暂停，而不是为已有投入继续增加功能。
