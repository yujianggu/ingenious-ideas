# Private file and recipient access boundary (Task 3)

Uploads are multipart `POST /api/files` with `owner_id`, `file`, and an `Idempotency-Key`. The server computes SHA-256 and size, chooses a UUID object key, and creates only `quarantined` metadata. Management writes require a tenant owner session, verified MFA and CSRF. `POST /api/files/{id}/validate` takes its own idempotency key; validation re-reads the private bytes, verifies size/hash, executes the scanner, then parses the actual format in a bounded subprocess. A clean, valid file becomes `ready`. Missing/tampered objects, unsupported extensions, malformed PDF/PNG/JPEG or detected malware become `rejected`. Scanner error/timeout/configuration absence returns 503 and leaves quarantine; retrying the same key is safe.

`GET /api/files/{id}/content` supports a single byte Range, including suffix/open-ended ranges. Every GET/Range/HEAD checks the current member or exact external grant, then the ready state. All gateway responses use `private, no-store`. The gateway never issues an OSS or signed download URL. Downloads already in flight are not forcibly interrupted on revocation.

Development uses `B16_PRIVATE_STORE=local` and `B16_PRIVATE_LOCAL_ROOT` outside public web roots. The directory is 0700 and objects are 0600; put is exclusive and names cannot contain paths. Scanner configuration is an explicit JSON argument array in `B16_SCANNER_COMMAND`, with exactly one `{file}` path substitution. No shell executes the array; return codes are 0 clean, 1 detected, anything else unavailable. A real ClamAV executable can be configured as `["/usr/bin/clamscan", "--database=/var/lib/clamav", "--no-summary", "{file}"]`. The environment-specific native development adapter is not clamscan and is not bundled with this project.

Production requires `DJANGO_SETTINGS_MODULE=config.settings.production`, `DJANGO_SECRET_KEY`, `B16_PRIVATE_STORE=oss`, HTTPS `B16_OSS_ENDPOINT`, `B16_OSS_BUCKET`, `B16_OSS_REGION`, `OSS_ACCESS_KEY_ID`, `OSS_ACCESS_KEY_SECRET`, `B16_SCANNER_KIND=clamav`, and a real executable clamscan command array with an existing `--database=...` path. The official OSS2 SDK uses V4 signatures, checks private bucket ACL and requests private object ACL plus forbid-overwrite on PUT. No public/CDN object access is supported. Cloud readiness remains subject to the opt-in real contract, not configuration checks.

`POST /api/access/{owner_id}/invitations` accepts a specific ready `file_id` and registered `receiver`. The 24-hour invitation response includes the opaque token and stable invitation ID. Only the token hash is stored. The opaque token is a secret-HMAC derivation of a random UUID, allowing an authorized idempotent issuance replay without putting bearer credentials in command receipts. Revocation/expiry are checked again before returning a replay.

An anonymous browser obtains the standard CSRF token, then posts `{token, receiver}` to `/api/access/challenge`. Before any provider call, a durable CodeDelivery reservation commits its UUID, code validation hash, browser binding, expiry and send budget. The six-digit code is secret-HMAC-derived from that random delivery UUID, so an uncertain provider acknowledgement retries the same code and provider request ID without storing plaintext codes. A separate idempotent dispatch command records acknowledgement. The code is tied to that browser. A code expires in five minutes; attempts and sends are limited and persisted. `/api/access/verify` accepts `{token, receiver, code}` and creates one external session with a maximum lifetime of 30 minutes, bounded by invitation expiry. All POSTs need distinct operation idempotency keys. The response identifies `external_recipient`, invitation, receiver, order and file; it never impersonates an employee and never returns a session capability. The HttpOnly Django session stores the grant ID. A separate signed HttpOnly browser cookie is issued at CSRF bootstrap and refreshed on challenge, scoped to /api. It survives Django session rotation. After a lost successful response or a failed session binding, only the original browser with the exact command key and payload can replay the committed grant; new keys cannot consume the code again. Grant expiry, invitation expiry and revocation are rechecked before rebinding. The verified recipient can access only that file, not other files in its order or tenant management APIs.

`POST /api/access/{owner_id}/revoke` revokes that order's invitations and all related external sessions under an Order lock. New GETs and Range requests return 403 immediately. A single invitation can be invalidated by `invalidate_invitation` from a transaction that holds its Order lock; Task 4 can bind a ConfirmationRequest to the stable invitation ID and invalidate superseded requests. The verification command's issuer foreign key is only a technical CommandReceipt partition; the human principal is the explicit external recipient.

Development code capture is explicitly configured with `B16_CODE_PROVIDER=identity.code_providers.DevelopmentCodeProvider`; it captures messages in process memory and does not send or log codes. Production rejects this adapter. Production requires `identity.code_providers.HTTPCodeProvider`, HTTPS `B16_CODE_PROVIDER_ENDPOINT` and `B16_CODE_PROVIDER_API_KEY`. That bridge posts `{receiver, code, request_id}` with an Authorization bearer key and an idempotency header; its response must be HTTP 200 JSON `{"accepted": true}`. No real supplier has been configured or contacted.

Run tests from `coding/backend`. Set `B16_TEST_SCANNER_COMMAND` to an actual scanner argument array to enable two real scanner tests; otherwise they skip explicitly. OSS is only exercised when `RUN_OSS_CONTRACT=1` and all five OSS environment variables are supplied. The contract uses a private disposable test bucket, checks PUT/GET, immutable writes, anonymous denial and gateway revoke/Range denial, and deletes its own test objects. Without credentials the cloud contract is **未执行**, never counted as cloud coverage.
