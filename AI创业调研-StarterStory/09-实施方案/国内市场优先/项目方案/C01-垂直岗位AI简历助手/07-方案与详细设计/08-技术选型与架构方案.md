## 结论与业务边界

采用 **顾问主导的事实台账与文档生成方案：Python + SQLite／JSON事实记录 + python-docx受控模板 + LibreOffice转PDF**。AI仅生成改写候选，顾问在已有办公工具编辑和核对，求职者确认事实后交付。重点是事实映射、文档一致性与可读排版，首版不建招聘、自动投递、评分或客户自助生成平台。

保持299元试单：15分钟访谈、经历母版、一个目标岗位版、事实映射、修改说明、核对卡及一次范围内修订。不同岗位另立任务。初期每周最多3单，先以2笔真实试单验证工时；已有电脑及办公软件可用、小团队低投入为暂定假设，采用Python的技术方向已确认。

## 数据与文档流

```text
岗位JD+原始经历 → 顾问追问 → 本人确认事实台账
 → JD要求与事实映射 → 人工/AI候选 → 顾问审核 → 本人核对
 → 同一已确认内容快照 → 母版/岗位版/修改说明/核对卡
 → DOCX + PDF一致性及版式检查 → 交付签认
```

顾问直接在DOCX修改后，修改内容必须同步回受控稿件或形成新的经过解析和核对的内容快照，再生成PDF和其他附件；禁止只改PDF或一个文件后仍宣布全套一致。输出带同一delivery_version和内容摘要，人工版式修改不能成为绕过事实确认的通道。

## 数据模型与事实规则

- Client → ServiceTask → FactVersion → DraftVersion → DeliveryVersion；每任务一个目标岗位。任务UUID独立于客户姓名和岗位名称。
- Fact保存原话、起止年月、个人职责、协作范围、成果、量化值及基数、证据类型、本人确认状态；无数据时标未知，不自动估算。
- ClaimMap把每条改写句子映射至一个或多个已确认事实ID；RequirementMap记录JD要求与事实支持或明确缺口。顾问意见不是新的事实来源。
- Question和Confirmation记录追问、回答、确认时间与原稿版本；Revision区分纠错、范围内改写和新增岗位。数字、任职日期或联系方式改变时，使全部受影响成果待重新生成及核对。
- 不要求身份证或无关证件；联系方式可脱敏，模型只需事实与岗位的最少文本。交付支持只能处理被分配任务的资料和版本；顾问才可审核专业表达；求职者确认的是本人事实，不是后台处理成功。

## AI边界

模型候选选择阿里云百炼 **Qwen Plus 系列的国内地域可用文本模型**，在样例评估后冻结具体模型 ID、地域、接口、参数和提示词版本；不在未评测时断言某个快照最优。官方文档提供结构化输出方式，但不同地域和快照的支持情况不同，因此不能仅凭系列名保证 JSON Schema 可用。实施前查实际模型能力，若不支持则使用文本／JSON输出加应用校验，最多2次受控重试后转人工，不自动换用境外端点。[百炼结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)、[模型能力与地域示例](https://help.aliyun.com/zh/model-studio/qwen-plus)、[可用模型查询](https://help.aliyun.com/zh/model-studio/list-models)。结构正确不代表事实正确；来源校验和专业审核必须保留。调用超时不推进审核状态，重试按任务及候选批次幂等登记，费用单独累计。

禁止根据JD添加不会的工具、放大任职时长、把团队业绩写成个人业绩或推算缺少基数的百分比。候选文本须保留fact_id列表；不存在或未确认的fact_id阻断采用。自动差异扫描提示新增数字、公司名、日期和技能，但不能证明真实性，所有数值由顾问逐条询证、本人确认。关闭模型后以同一事实表人工改写，完整服务仍可交付。

## 验收映射

| 需求 | 实施机制 | 计划放行测试 |
| --- | --- | --- |
| R01、R02、A01、A03 | 事实表+追问+岗位映射 | JD中无经历支持的技能标缺口；无基数的百分比不进入终稿 |
| R03、N02 | ClaimMap和本人确认 | 每句经历有来源；每个数字可指向本人确认，未知事实不输出为确定事实 |
| R04、R06、R07、A07 | 独立岗位任务、修订版本 | 新岗位不覆盖旧稿；退回后不能确认旧终稿；缺陷修复不占范围内改写次数 |
| R05、A02、A06 | 单一内容快照生成全套 | 日期从一年改半年后所有成果一致；电话不同即阻断交付 |
| R05、A04—A05 | PDF逐页审查及复制文本检查 | 无断字、截断、空页；复制粘贴顺序连贯，DOCX与PDF关键字段完全一致 |
| N01 | 客户目录与导出清单 | 两名同姓名用户不串资料，导出包无他人附件或内部追问私注 |

单栏版式是降低文本读取和换页复杂度的设计选择，不承诺任何ATS评分或面试结果。最低验证覆盖短经历、长项目、中文长岗位名、中英文混排和两页换页；在实际目标办公软件打开DOCX，并对PDF逐页人工检视。

## 实施顺序与成本假设

先完成1单人工文档基准，再自动化确定性环节。技术工作建议共12小时：4小时事实台账和访谈字段、4小时模板与四类成果生成、4小时一致性检查和恢复演练；首两周剩余28小时留给访谈、顾问审核及付费试单，不把选型转成平台研发。只有连续试单显示重复排版耗时明显，才继续做内部工作台。

原单价299元、模型处理8元／单、审核45分钟60元和客服修订20分钟26.67元继续作为预算假设；8元不是模型供应商报价。是否包含15分钟访谈必须逐单计时，若另计则原获客后贡献从126.34降到106.34元。现有设备可用时新增服务器费为0；人工办公许可、字体许可或存储如需新购，单独计入，不含在“免费开源”结论里。首两周外部现金上限500元、首批每周最多3单仍约束实施计划。费用超预留或修订超过预算时调整接单范围和报价，不让自动草稿替代顾问。

## 部署、操作权限与恢复

首版由指定交付人员在现有电脑运行固定 Python 虚拟环境；依赖版本和文件摘要锁定，安装包来自官方分发并留档，客户原件不进 Git。SQLite 只存元数据、状态、索引；原件和导出文件按客户 UUID／任务 UUID／版本分目录，文件名不作为权限依据。单次作业领取锁，成功后事务提交状态，失败不覆盖旧交付。CLI 的任务参数必须匹配客户清单，导出同时校验 manifest 中的客户 ID、任务 ID 和全部文件摘要。

首版没有客户登录服务，也不把原型角色开关移作权限控制。客户通过约定收件渠道交资料，交付人员记录实际发送者及确认记录；本地 OS 账户仅授权交付人员，客户只取得本任务成果。多人同时编辑时再启动内部工作台评估，并增加服务端身份、逐任务授权、审计与并发控制；不得把 SQLite 文件放在共享网络盘上让多人直接写。

每天工作结束并在交付前做一次一致备份：SQLite 使用 Backup API，冻结的文件目录与摘要清单一同加密保存到独立备份介质；密钥单独保管。[SQLite 官方 Backup API](https://www.sqlite.org/backup.html)支持运行中数据库的一致备份，但附件一致性仍由作业冻结和清单校验实现。规划恢复点不超过一个工作日、恢复时间不超过4小时，属于待演练目标，不能当现成承诺。首单前在空目录还原，核对行数、文件摘要、旧版与最新状态，并实际打开交付文件。保留期限与删除周期在收件约定中确认；到期覆盖原件、派生稿和备份轮换，不假定删数据库就已删除全部资料。

不采购服务器、对象存储或自建 GPU。若客户约定需要国内云备份或多人远程访问，再单列地域、存储、访问费用及授权评审；本地方案不能推出“本地运行就没有模型外发”。任何模型调用前都需确认允许外发的字段与教材范围，去掉无关身份信息，密钥只在 OS 密钥库或受限运行环境保存。
